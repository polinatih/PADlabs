# Лабораторная работа №1 — RAG-система по Marvel Cinematic Universe (MCU)

## Предметная область

Датасет собирается из англоязычной Wikipedia и охватывает вселенную
Marvel Cinematic Universe (MCU): фильмы, сериалы, персонажей и актёров.

Сознательно **не включены** фильмы про тех же персонажей, снятые другими
студиями (Sony, Fox) до перехода прав к Marvel Studios — например,
Spider-Man (2002), Fantastic Four (2005), Elektra (2005). Это разные
вселенные с разными актёрами и сюжетами, не связанные с MCU напрямую.
Смешивание их с MCU усложнило бы оценку качества системы (одинаковые
имена персонажей отсылали бы к разным, несвязанным фактам).

## Сбор данных (grabber)

Файл: `src/grabber/wiki_grabber.py`

> **Исправление после проверки датасета.** Первая версия брала с каждой
> страницы-хаба только первые 300 ссылок. Wikipedia отдаёт ссылки по
> алфавиту, поэтому в датасет попали лишь названия примерно от A до I:
> отсутствовали Thor, Spider-Man, Black Panther, Avengers: Endgame и
> большинство актёров. Кроме того, при ошибке запроса (HTTP 429) статья
> молча считалась «не по теме». Теперь обходятся все ссылки, упавшие
> запросы повторяются, категории запрашиваются пачками по 50, редиректы
> не создают дубликатов, а тег статьи определяется по её категориям.
> Поведение проверяется тестом на имитации API (`tests/test_grabber.py`).

### Как это работает

Прямая категория Wikipedia "Marvel Cinematic Universe films" оказалась
неинформативной — она содержит в основном служебные страницы-списки, а
не сами статьи о фильмах (отдельные статьи о фильмах вообще не лежат в
одной плоской категории на Wikipedia).

Поэтому используется двухшаговая схема:

1. Берутся несколько страниц-хабов (списков):
   - `List of Marvel Cinematic Universe films`
   - `List of Marvel Cinematic Universe television series (Marvel Studios)`
   - `List of Marvel Cinematic Universe film actors`
   - `Characters of the Marvel Cinematic Universe`
2. Через Wikipedia API (`prop=links`) собираются все ссылки на другие
   статьи с каждой такой страницы.
3. Для каждой ссылки дополнительно проверяются категории самой статьи
   (`prop=categories`). Статья принимается, только если её категории
   подтверждают релевантность:
   - фильмы/сериалы/персонажи — категория содержит "Marvel Cinematic
     Universe";
   - актёры — категория содержит год рождения (например "1990 births"),
     так как исходная страница-хаб уже curated и содержит только реальных
     актёров MCU.
4. Текст статьи скачивается через `prop=extracts&explaintext=1` (чистый
   текст без wiki-разметки).
5. Каждая статья сохраняется как отдельный `.json` файл с metadata
   (title, url, tag, content_hash, fetched_at).

### Защита от дублей и повторный запуск

Перед сохранением считается SHA-256 хэш текста. Если файл с таким же
названием и хэшем уже существует — статья помечается как `unchanged` и
не перезаписывается. Если текст изменился — `updated`. Новая статья —
`new`. Это позволяет запускать grabber повторно (например, если
Wikipedia обновилась) без создания дубликатов.

### Обработка ошибок

Wikipedia API иногда отвечает `429 Too Many Requests`. Grabber не
прерывается при такой ошибке, а ждёт и повторяет запрос (до 4 попыток
с увеличивающейся паузой).

## Известные ограничения (для раздела "исследовательская часть")

1. **Небольшая доля ложных срабатываний фильтра.** Несколько статей о
   персонажах из фильмов Sony 2002 года (`Peter Parker (2002 film
   series character)`, `Norman Osborn (2002 film series character)` и
   похожие) прошли фильтр, несмотря на то что не относятся к MCU.
   Предположительно, у этих статей в категориях Wikipedia всё же
   упоминается "Marvel Cinematic Universe" в контексте
   кросс-медийных адаптаций персонажа. Доля таких статей в датасете
   мала (единицы из 200+), и в дальнейшем анализе они будут исключены
   вручную или отфильтрованы дополнительной проверкой на этапе
   preprocessing.
2. **В датасет попал не только "сюжетный" контент**, но и саундтреки,
   отдельные песни, видеоигры и документальные шоу (например
   "Marvel Studios: Assembled"). Это тоже часть категории "Marvel
   Cinematic Universe" на Wikipedia, но менее полезно для ответов на
   вопросы о сюжете. Решение: оставить как есть на этапе сбора данных,
   при необходимости отфильтровать по типу контента на этапе
   preprocessing (по длине текста / наличию инфобокса фильма).

## Обработка данных и chunking

Файл: `src/preprocessing/preprocess.py`

Текст очищается от технического мусора Wikipedia (сноски `[1]`,
`[citation needed]`, лишние пустые строки) и разбивается на chunks
четырьмя способами для последующего сравнения на этапе retrieval:

| Стратегия       |  Chunks | Средняя длина, симв. |
|-----------------|--------:|----------------------:|
| fixed           |   7 965 | 489 |
| fixed_overlap   |   9 841 | 490 |
| paragraph       |   3 551 | 1 097 |
| headers         |   2 787 | 1 365 |

Механические стратегии (`fixed`, `fixed_overlap`) дают много мелких
одинаковых по размеру кусков (overlap добавляет чанки за счёт
пересечений, не меняя их среднюю длину). Стратегии, учитывающие
структуру текста (`paragraph`, `headers`), дают меньше, но более
смыслово цельных и крупных кусков. Какая из них лучше для поиска,
проверяется позже, на этапе retrieval evaluation.

## Embeddings и Vector Store

Файлы: `src/embeddings/embedders.py`, `src/embeddings/build_index.py`

Сравниваются две бесплатные локальные модели (статьи на английском,
поэтому английские модели):

| Ключ    | Модель                                   | Размерность | Макс. вход | Почему выбрана |
|---------|------------------------------------------|------------:|-----------:|----------------|
| minilm  | sentence-transformers/all-MiniLM-L6-v2   | 384 | 256 токенов | быстрая, лёгкая, стандартный baseline |
| bge     | BAAI/bge-small-en-v1.5                   | 384 | 512 токенов | того же размера, но в бенчмарках поиска обычно сильнее; для запросов использует специальный префикс |

Одинаковая размерность выбрана намеренно: различие в результатах можно
связывать с качеством модели, а не с размером вектора.

**Vector DB: ChromaDB.** Работает локально без сервера, хранит данные на
диске, поддерживает фильтры по metadata (нужны для этапа filtering). Для
~25 тыс. chunks её более чем достаточно. Альтернативы: FAISS (быстрее на
миллионах векторов, но не хранит текст и metadata - их пришлось бы вести
отдельно), Qdrant/Milvus (требуют отдельного сервера - избыточно здесь).

Для каждой пары (стратегия chunking x модель) создаётся отдельная
коллекция `<strategy>__<model>` (например `headers__bge`), всего 8
коллекций. Метрика близости - cosine.

**Важная деталь для анализа:** модель молча обрезает вход по лимиту
токенов. Chunks по заголовкам в среднем ~1365 символов (~330 токенов),
поэтому MiniLM (лимит 256) не увидит часть их текста. `build_index.py`
считает долю обрезанных chunks для каждой коллекции - эти числа нужно
учитывать при сравнении стратегий.

Запуск: `pixi run python src/embeddings/build_index.py`
(опции: `--strategies`, `--models`, `--limit N` для быстрой пробы).
Повторный запуск пропускает уже проиндексированные chunks.
